# ⚖️ 架構決策與工程權衡紀錄 (Decision Log & Trade-offs)

本文件詳述 **NTU PoolFlow 未游先知** 在系統設計、架構選型、邊界防禦與演算法實作時所面臨的關鍵技術決策與權衡思考。

---

## 🎯 決策 1：網頁爬蟲選型 —— 輕量容錯 Regex vs. 重型 DOM 解析器 (JSDOM / Cheerio)

### 背景與挑戰
台大綜合體育館官網未提供標準 API，僅於公開網頁顯示即時人數。系統必須每 5 分鐘主動採樣一次。

### 權衡考量
| 方案 | 優點 | 缺點 |
| :--- | :--- | :--- |
| **方案 A：JSDOM / Cheerio** | 語意化佳，支援標準 CSS 選擇器。 | 依賴 Node.js 原生環境，套件體積大（數 MB），冷啟動延遲高，難以在輕量邊緣 Worker 運行。 |
| **方案 B：嚴格字符索引定位** | 零相依、速度最快。 | 網站只要微調空白字元或 HTML 標籤，立即報錯。 |
| **方案 C：非貪婪正規表達式 + Fallback（採用）** | 零外部依賴、記憶體佔用小於 1MB、執行時間 < 1ms。 | 需嚴謹設計 Regex pattern 與邊界防禦測試。 |

### 最終決策
採用 **方案 C**。使用精準的非貪婪捕獲模式匹配數值節點，並在解析層配置三層安全防禦：
1. **數值邊界校驗**：限制合理範圍 $[0, 150]$，防止爬到 NaN 或異常極端值。
2. **Fallback 機制**：若解析失敗，自動退回上一期紀錄或預設值，保障服務不中斷。
3. **破壞性測試保護**：以 Vitest 覆蓋 HTML 標籤缺損、格式突變等多種邊界測試。

## 🎯 決策 2：預測機制選型 —— 輕量差分演算法 vs. 機器學習模型 (LSTM / Prophet)

### 背景與挑戰
為了提前預警即將湧入的人潮，系統需要具備預測趨勢的能力。

### 權衡考量
| 評估維度 | 機器學習模型 (LSTM / Prophet) | 短期時序差分預測演算法（採用） |
| :--- | :--- | :--- |
| **啟動門檻** | 需數月標籤資料、天氣、假期等豐富特徵。 | **零歷史冷啟動**，僅需現場 15 分鐘連續 4 筆數據即可運作。 |
| **邊緣開銷** | 需 Python Runtime 或 ONNX 運行環境，冷啟動高。 | **純 TypeScript 實作**，在邊緣端即時計算，耗時 < 0.1ms。 |
| **可解釋性** | 黑箱模型，難以直觀解釋門檻調動理由。 | **高度透明**，依 3:2:1 時間權重與變化率直觀微調燈號門檻。 |
| **防過度敏感** | 突發特殊事件容易造成模型過擬合或產生過度反應。 | 設有 0.5 緩衝係數與 $\pm 8$ 人最大微調限制，避免跳動過大。 |

### 最終決策
在輕量、零維護成本與邊緣高可用性優先的前提下，選擇**「短期時序差分加權演算法」**。運算成本極低、完全透明可解釋，且能精準捕捉 90% 的短時間急湧人流。

## 🎯 決策 3：開館救生員底數（Baseline）自動校正

### 背景與問題
台大泳池每天開館時（平日 08:00 / 週末 09:00），早在開門前半小時（07:30 / 08:30），救生員、清潔人員與教練就已經刷卡進場就位（約 2~10 人）。  
如果直接呈現官網數字，會造成「明明剛開館或還沒開，水下就顯示有人」的怪異現象。

### 解決方式
1. **提早 30 分鐘開始採樣**：爬蟲提前在 07:30（週末 08:30）啟動，記錄開館時的第一筆底數作為 `Baseline`。
2. **扣除底數還原真實泳客數**：前端顯示的水下淨人數為 `現場人數 - 救生員底數`。
3. **防負數保護**：如果開館初期人數極少（例如剛進來 1 人，而底數為 4 人），相減後強制保底為 **0 人**，避免畫面上出現負數。

## 🎯 決策 4：邊緣運算 UTC 時區防護（避免時差 Bug）

### 背景與踩坑
Cloudflare Workers 邊緣伺服器預設運行在國際標準時間（`UTC`）。若使用一般的日期轉型函式，在午夜 00:00 容易重複觸發 `+8 小時` 轉換，導致系統在半夜誤以為是早上而錯誤判定為開館。

### 解決方式
全面改用標準的 `Intl.DateTimeFormat`，嚴格鎖定 `Asia/Taipei` 時區做單一格式化，確保時區判定永遠正確無誤。

## 🎯 決策 5：歷史紀錄膨脹與 API 滑動視窗（Sliding Window）

### 背景與效能問題
Cloudflare KV 資料庫存放數個月以來的 5 分鐘紀錄，累積已超過 24,000 筆（JSON 原始大小超過 1.4 MB）。若每次開啟網頁都全部回傳，會導致：
* 浪費邊緣傳輸頻寬。
* 行動端手機瀏覽器解析 1.4 MB JSON 產生明顯卡頓。

### 解決方式
在後端加入 `getActiveWindowHistory(14)` 滑動視窗機制，API 只回傳最近 14 天的活躍數據：
* **傳輸資料量**：從 **1.42 MB** 縮減至 **~95 KB**（節省 **93% 頻寬**）。
* **手機首屏載入**：顯著提升首屏載入速度，達到秒開效果。

## 🎯 決策 6：常態歷史曲線（Typical History Curve）邊緣端聚合、每日獨立 Baseline 扣除與 5 分鐘網格插值

### 背景與問題
若僅直接將歷史原始人數在前端做純平均，會產生三大失真問題：
1. **工作人員底數浮動失真**：不同日期的開館底數（救生員/教練人數）不一致（例如有些日子為 2 人，有些日子為 8 人），若用今日 Baseline 扣除歷史平均，早晨時段容易出現負數或虛高。
2. **無效/休館日稀釋均線**：若過去 14 天中包含了全天數值為 0 的異常紀錄（例如颱風休館、場館保養維修或爬蟲初次建置），直接納入計算會將正常營運日的真實人數除以 2 腰斬。
3. **採樣未對齊與梳狀鋸齒**：歷史爬蟲採樣若有間隔跳躍（例如 14:05、14:35），而今日嚴格每 5 分鐘採樣，前端逐點比對時會因整點落空而突降至 0，形成折線圖忽高忽低的梳狀尖刺。

### 解決方式
在 Edge Worker 後端實作 `calculateNetTypicalHistory` 預聚合引擎：
1. **每日獨立 Baseline 扣除**：每個歷史日先扣除各自當天的開館 Baseline，還原純淨的淨泳客走勢。
2. **全天無效日自動濾除**：檢查歷史日淨人數峰值（`maxNet`），若整天為 0 則判定為休館/測試日，自動排除在統計之外。
3. **5 分鐘網格線性插值（Linear Interpolation & Forward Fill）**：在官方開放時段內建立標準 5 分鐘網格，45 分鐘內的採樣間隔自動以斜率插值平滑填補，徹底消除均線墜落至 0 的鋸齒。

## 🌐 產業對標與潛力發展 (Industry Benchmarks & Future Potential)

本專案從泳客痛點出發，以「外部即時數據感知與動態預測」切入。在專業體育運動科技與智慧場館領域，已有成熟企業將水下安全與人流監控推向更高層次：

1. **[煊恩科技 (Xuanen)](https://www.xuanen.com.tw/)**  
   * **產業定位**：台灣領先的水上活動安全與智慧運動場館系統整合商。  
   * **核心能量**：整合水質監控、場館人流即時管理、救生輔助防溺系統與自動化控制，提供專業場館一站式軟硬體解決方案。
2. **[Lynxight](https://www.lynxight.com/)**  
   * **產業定位**：全球頂尖的 AI 水下視覺感知與智慧救生安全分析系統。  
   * **核心能量**：利用標準泳池現有監視鏡頭，結合邊緣 AI 深度學習演算法，進行水下即時泳客追蹤、溺水早期預警、泳道密度與人流行為深度分析。

### 本專案未來演進潛力
* **短期擴展**：對接中央氣象署降雨 API 與校園行事曆（考試週、寒暑假），補足中長期的天氣干擾因素。
* **中期升級**：將演算法介面抽象化，橫向擴展支援台科大、台師大或雙北公立運動中心。
* **長期願景**：若未來能與如煊恩科技或 Lynxight 這類專業場館硬體與 AI 視覺監控方案對接，將能從「閘門刷卡總數」進一步深入到「各泳道即時水下密度精確分流」，打造全方位的智慧水上運動生態。
