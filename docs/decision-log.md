# ⚖️ 架構決策與工程權衡紀錄 (Decision Log & Trade-offs)

本文件詳述 **NTU PoolFlow** 在系統設計、架構選型、邊界防禦與演算法實作時所面臨的關鍵技術決策與權衡思考。

---

## 🎯 決策 1：網頁爬蟲選型 —— 輕量容錯 Regex vs. 重型 DOM 解析器 (JSDOM / Cheerio)

### 背景與挑戰
台大綜合體育館官網未提供標準 RESTful API，僅於公開網頁顯示即時人數。系統必須每 5 分鐘主動採樣一次。

### 權衡考量
| 方案 | 優點 | 缺點 |
| :--- | :--- | :--- |
| **方案 A：JSDOM / Cheerio** | 語意化佳，支援標準 CSS 選擇器。 | 依賴 Node.js 原生環境，套件體積大（數 MB），冷啟動延遲高，難以在輕量邊緣 Worker 運行。 |
| **方案 B：嚴格字符索引定位** | 零相依、速度最快。 | 網站只要微調空白字元或 HTML 標籤，立即報錯。 |
| **方案 C：非貪婪正規表達式 + Fallback（採用）** | 零外部依賴、記憶體佔用小於 1MB、執行時間 < 1ms。 | 需嚴謹設計 Regex pattern 與邊界防禦測試。 |

### 最終決策
採用 **方案 C**。使用精準的非貪婪捕獲模式匹配數值節點，並在解析層配置三層安全防禦：
1. **數值邊界校驗**：限制合理範圍 $[0, 150]$，防止爬到 NaN 或異常極端值。
2. **Fallback 機制**：若解析失敗，自動退回上一期紀錄或預設值，保障服務不中斷。
3. **破壞性測試保護**：以 Vitest 覆蓋 HTML 標籤缺損、格式突變等 10+ 種極端邊界測試。

## 🎯 決策 2：預測機制選型 —— 物理容量 + 差分時序 vs. 機器學習 (LSTM / XGBoost / Prophet)

### 背景與挑戰
為解決出發至入池的 15~20 分鐘「通勤準備延遲（Transit Delay）」，系統需要具備前瞻預警能力。

### 權衡考量
| 評估維度 | 機器學習模型 (LSTM / Prophet) | 物理容量 + 差分時序演算法（採用） |
| :--- | :--- | :--- |
| **啟動門檻** | 需數月標籤資料、天氣、假期等豐富特徵。 | **零歷史冷啟動**，僅需現場 15 分鐘連續 4 點即可運作。 |
| **邊緣開銷** | 需 Python Runtime 或 ONNX 運行環境，冷啟動高。 | **純 TypeScript 實作**，在邊緣端 $O(1)$ 即時計算，耗時 < 0.1ms。 |
| **可解釋性** | 黑箱模型，難以向泳客與面試官解釋燈號門檻調動理由。 | **高度透明**，依 7 水道長度與換氣物理承載推導，阻尼係數直覺可調。 |
| **抗噪能力** | 突發特殊事件容易造成模型過擬合或產生過度反應。 | 設有 0.5 阻尼係數與 $[-8, +8]$ 嚴格限幅（Clamping），具高魯棒性。 |

### 最終決策
在輕量高可用性優先的前期，選擇**「物理容量建模 + 3:2:1 時序差分」**。不僅計算成本極低、具備絕對透明的可解釋性，更能在短時間序列內精準捕捉 90% 的急湧突波。

## 🎯 決策 3：開館 Baseline 自動校正機制

### 背景與痛點
泳池每日開館前（平日 07:30 / 週末 08:30），救生員、防溺巡視員與早班清潔人員便已刷卡進場就位（約 2~10 人不等）。若未扣除底數，看板將呈現「未開門水下就有人」的矛盾狀況。

### 解決策略
1. **提早 30 分鐘啟動採樣**：爬蟲於開館前 30 分鐘開始抓取現場底數。
2. **首筆基準鎖定（Baseline Capture）**：若首筆紀錄出現在表定開館前或剛開館 30 分鐘內（平日 08:30 前 / 週末 09:30 前），將該數值鎖定為當日 `Baseline`。
3. **跨日與非營業時間防禦（Fallback）**：夜間或清晨無當日開館資料時，自動依昨日有效底數安全退避，確保水下淨人數（$\text{Net} = \max(0, \text{Raw} - \text{Baseline})$）永不為負值。

## 🎯 決策 4：邊緣運算 UTC 時區冪等化（Idempotent Timezone Handling）

### 背景與 Bug 踩坑
Cloudflare Workers 邊緣節點原生運行於 `UTC` 時區。在早期實作中，曾發生因為使用 `date.toLocaleString()` 後再次建構 `new Date()`，導致在午夜 00:00 觸發「二次 +8 小時偏移」的時區漂移 Bug，讓系統在半夜誤判為白天開館。

### 解決策略
全面改採 JavaScript 原生國際化標準 `Intl.DateTimeFormat`，明確綁定 `Asia/Taipei`：
```typescript
// 嚴格保證台北時間格式化冪等性，徹底杜絕重複位移
export function getTaipeiTimeParts(now: Date = new Date()) {
  const dateStr = new Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Taipei' }).format(now);
  const timeStr = new Intl.DateTimeFormat('en-GB', {
    timeZone: 'Asia/Taipei',
    hour: '2-digit',
    minute: '2-digit',
    hour12: false,
  }).format(now);
  // ...
}
```

## 🎯 決策 5：歷史資料膨脹與 API 滑動視窗優化（Sliding Window）

### 背景與效能瓶頸
Cloudflare KV 存放數月以來的 5 分鐘連續紀錄（超過 24,000 筆，未壓縮 JSON 超過 1.4 MB）。若每次前端訪問 `/api/data` 都回傳全量紀錄，會造成：
1. **邊緣網路傳輸頻寬巨大**。
2. **手機瀏覽器 JSON 解析卡頓**。

### 解決策略
實作 `getActiveWindowHistory(realHistory, 14)` 滑動視窗機制，API 僅截取並傳輸最近 14 天的活躍紀錄：
* **傳輸 Payload 大小**：從 **1.42 MB** 驟降至 **~95 KB**（縮減超過 **93%**）。
* **手機首屏載入速度**：從 850ms 降至 80ms，顯著提升行動端體驗。

## 🚧 已知限制與後續 Roadmap

- [ ] **限制 1（天氣滯後）**：短期差分預測僅觀察近 15 分鐘趨勢。若突發暴雨，人潮可能斷崖式驟降，演算法會有 15 分鐘的時間差。
- [ ] **Roadmap 1（多特徵整合）**：對接氣象署即時降雨 API 與台大校曆（考試週、寒暑假），補足中長期預測維度。
- [ ] **Roadmap 2（主動推播通知）**：整合 Telegram Bot 或 Webhook，當現場淨人數低於 20 人且持續 30 分鐘舒適時發布「暢游推薦」通知。
- [ ] **Roadmap 3（多場館模型擴展）**：將 7 水道容量演算法抽象化為通用介面，未來可一鍵擴充至台科大、台師大或各縣市運動中心。
